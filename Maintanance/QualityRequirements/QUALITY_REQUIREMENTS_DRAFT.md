# swift-ac-library Quality Requirements Draft

> **文書状態:** 原案。製品品質要求の正本ではない。
>
> 本書は、`Maintanance/User/CONCEPT_DEFINITION.md` の暫定コンセプトから品質要求を検討するための作業文書である。
> 内容の採用、優先順位、達成水準、保証範囲、および正本化は、今後のユーザー判断に委ねる。

## 1. 位置づけ

本書は、次の暫定コンセプトを上位概念として、swift-ac-library に必要と考えられる製品品質を整理する。

> ac-libraryを製品レベルでSwift環境に供すること

品質要求は、この製品コンセプトの成立に必要な性質を表す。

QR-01〜QR-07は、上位品質要求の分類と方向を定める。個別の製品、module、または機能への適合判定には、対象、達成水準、証拠、および受入条件を下位文書で具体化する必要がある。本書のQRだけを直接の合否基準として使用しない。

本書では、個別APIの仕様、達成水準、検証方法、受入条件、リリース工程を確定しない。
既存の実装、テスト、ベンチマーク、CI、および文書は品質要求そのものではなく、要求の具体化や評価に利用し得る品質資産として扱う。

テストや実装がすでに存在することを理由に、保証範囲や製品方針を既成事実として確定しない。

## 2. 製品コンセプトの暫定的な解釈

暫定コンセプトは、少なくとも次の二つの要素を含むと解釈できる。

- C1 — ac-library として認識できる機能、意味、および利用価値を備えること。
- C2 — Swift のエコシステムにおいて、製品として導入、理解、利用、保守できること。

この二つは独立ではない。

本家 ac-library への忠実さを優先する場合でも、Swift の型、所有権、メモリ安全性、toolchain、およびパッケージ利用の性質を不必要に損なってはならない。
一方、Swiftらしい表現や一般利用への対応によって、競技プログラミングで必要な予測可能性、性能、移植可能性、および本家との対応関係を不必要に損なってはならない。

C1とC2が衝突する場合は、実装上の都合だけで解決せず、具体的な差異、各利用文脈への影響、および選択肢を分離して製品判断へ返す。

現時点では、次の語の厳密な意味は未確定である。

- 「ac-library」が要求する互換性の範囲
- 「製品レベル」の具体的な達成条件
- 競技プログラミング用途と一般Swift開発用途の保証範囲
- 本家C++実装に対する性能上の目標
- 対応するSwift、platform、architecture、およびbuild configuration

これらは実装や既存テストから逆算せず、今後の品質要求の具体化で判断する。

## 3. 上位品質要求案

### QR-01 ACL適合性 — ac-libraryとして対応関係を説明できる

提供対象とする機能は、基準とする本家 ac-library の機能、意味、前提条件、および計算量との対応関係を持つこと。

意図的な差異、Swiftへの移植によって生じる差異、未対応機能、および基準とする本家の版や状態を識別できること。

同じ結果を返すことだけで互換性全体を確認済みとせず、公開API、事前条件、失敗条件、計算量、および数値表現など、必要な互換性の次元を個別に扱うこと。

- コンセプト: C1、C2
- 主な関心: 機能適合性、互換性、追跡可能性

### QR-02 正確性 — 公開契約に従って正しく振る舞う

各アルゴリズムおよびデータ構造は、公開契約で定めた入力、操作、状態遷移、および結果に従って、一貫した振る舞いを提供すること。

本家由来の仕様だけでは定まらないSwift固有の型、オーバーロード、Collection入力、文字列、整数表現、および所有権に関する振る舞いも、公開する範囲について契約を定めること。

不正入力や事前条件違反に対する振る舞いを、通常の正確性と区別して明確にすること。

- コンセプト: C1、C2
- 主な関心: 機能適合性、信頼性

意図的に本家と異なるAPIまたは振る舞いでも、その差異と影響をQR-01に従って説明でき、Swift製品として定めた公開契約をQR-02に従って満たすなら、差異だけを理由に直ちに不適合とはみなさない。

### QR-03 性能効率性 — 想定用途で実用的な性能特性を持つ

提供対象とする機能は、競技プログラミングおよび明示した一般Swift利用の文脈で、実用可能な時間・空間特性を持つこと。

計算量、実行時間、メモリ使用量、allocation、入力規模への応答、およびbuild configurationによる差を扱うこと。

相対的な性能回帰の防止と、本家C++実装または別途選定した比較対象との外部比較を区別すること。
比較対象、workload、環境、および受入水準は、下位の品質プロファイルまたは評価計画で具体化する。

`-Ounchecked` など保証境界を変える構成の測定を、通常構成の適合証拠として無条件に扱わないこと。

- コンセプト: C1、C2
- 主な関心: 性能効率性、利用文脈への適合

### QR-04 Swift上の安全性 — 低レベル実装の危険を不必要に利用者へ転嫁しない

ポインタ、直接メモリ管理、`ManagedBuffer`、非コピー型、unchecked操作その他の低レベル手段を利用する場合でも、公開契約に含まれる所有権、排他性、要素寿命、初期化と破棄、Indexの有効性、およびメモリ安全性を維持すること。

Debug、Release、最適化設定、platform、architecture、およびSwift toolchainによって保証範囲が異なる場合は、その境界を明確にすること。

事前条件違反と、正しい利用から到達し得る未定義動作またはメモリ破壊を区別すること。

- コンセプト: C2
- 主な関心: 信頼性、セキュリティの関連側面、Swift言語契約

本要求が現在中心として扱うのは、メモリ安全性およびSwift言語契約に関係する安全性である。依存供給、改ざん、脆弱性対応など、その他のセキュリティ品質を製品要求に含めるかは未決とする。

### QR-05 理解可能性 — 利用者がAPIと保証境界を理解できる

本家 ac-library の利用経験者とSwift利用者の双方が、公開APIの目的、操作、型、制約、計算量、失敗条件、および本家との差異を理解できること。

利用者向け文書、コード例、API宣言、および実際の振る舞いが整合すること。

アンダースコアを含む宣言など、公開可視性と互換性保証の範囲が一致しないものについて、利用者が保証対象を誤認しないようにすること。

- コンセプト: C1、C2
- 主な関心: 相互作用能力、利用者支援

### QR-06 利用可能性 — 対象環境で導入し利用できる

保証対象とする競技プログラミング環境および一般のSwift開発環境で、パッケージを導入、build、import、および利用できること。

対応するSwift toolchain、platform、architecture、依存関係、build configuration、package trait、提供する版・系列、および公開APIの互換性範囲を明確にすること。

release、互換保守系列、および開発系列のうち、利用者へ提供する版と保証範囲を識別できること。Git branchは現在の提供管理手段であり、品質要求によって特定のGit運用を固定しない。

ある環境での成功を、他の環境での利用可能性の証拠として無条件に扱わないこと。

- コンセプト: C1、C2
- 主な関心: 互換性、移植性、柔軟性

### QR-07 持続可能性 — 本家とSwiftの変化を追跡しながら保守できる

#### 製品・設計の保守可能性

本家 ac-library、Swift言語、compiler、標準ライブラリ、platform、および依存パッケージの変化に対して、既存の機能、互換性、性能、および安全性への影響を分析できること。

本家由来の部分、Swift移植固有の部分、回帰防止のための部分、および探索的な部分を識別し、変更理由と検証範囲を追跡できること。

#### 品質情報を次工程へ接続する運用能力

品質上の問題、反証、未検証領域、および残余リスクを、次の仕様、実装、検証、および文書へ接続できること。

この運用能力を製品品質要求に含めるか、品質アセスメントおよび開発運用の原則として分離するかは未決とする。

- コンセプト: C1、C2の継続的成立
- 主な関心: 保守性、柔軟性、追跡可能性

## 4. VerificationとValidation

### Verification — 具体化された要求を満たすか

公開仕様および具体化された品質要求に対し、製品が要求された性質を備えるか検証する。

テストを仕様として利用しつつ、その出所、観測対象、実行条件、および証明できない範囲を明確にする。
必要に応じて、静的解析、Sanitizer、性能測定、設計上の根拠、異なるtoolchainやplatformでのbuild・実行、および独立レビューを組み合わせる。

### Validation — コンセプトが実際の利用で成立するか

品質要求の組み合わせによって、ac-libraryを製品レベルでSwift環境に提供できているかを確認する。

特に、次の問いを扱う。

- 本家 ac-library の利用者が、対応関係と差異を理解して移行または併用できるか。
- AtCoderを含む競技プログラミング環境で実際に導入し利用できるか。
- 一般のSwift Packageとして無理なく導入し利用できるか。
- 必要な性能とSwift上の安全性が両立しているか。
- 文書が利用者の判断に必要な契約と保証境界を伝えているか。

Verificationの成功だけからValidationの成功を推定しない。

Validationでは、公開前の代理Validationと公開後の実利用Validationを区別する。代表利用scenario、実際の競技提出、Swift Packageのconsumer fixture、第三者レビュー、および公開後の利用実績は、それぞれ異なる範囲の証拠として扱う。実利用実績だけをValidationの唯一の手段とはしない。

## 5. 品質アセスメントの原則案

品質アセスメントでは、要求ごとに少なくとも次を区別する。

- 確認済み
- 未達
- 未検証
- 対象外
- 受容済みの残余リスク

証拠が不足している場合は、実装の存在、テスト件数、CI全体の成功、過去の利用実績、またはAI同士の合意だけによって適合を主張しない。

警告、失敗、skip、not run、環境差、測定揺らぎ、仕様との矛盾、および既存主張への反証は、解消前に評価上の証拠として保存する。

問題を非表示にすること、検査対象から除外すること、および原因を解消することを区別する。

要求、評価対象、前提、または証拠が変化した場合は、その影響範囲を確認してから従来の適合判断を再利用する。

## 6. 既存テストおよび品質資産の整理原則案

既存テストは、一つの分類だけに押し込まず、少なくとも「由来」と「品質上の役割」を分けて記録する。

### 由来

- 本家 ac-library または本家テストに由来するもの
- Swiftへの移植差異を検証するために追加したもの
- 発見済み不具合の回帰防止として追加したもの
- 性能、stress、実装方式などの探索として追加したもの
- 使用例、実験、または個人的関心から追加したもの
- 由来を確認できないもの

### 品質上の役割

- ACL適合性
- 公開契約の正確性
- Swift固有の型・所有権・要素寿命・メモリ安全性
- 事前条件および失敗境界
- platform、toolchain、build configurationの互換性
- 性能回帰
- 外部性能比較
- 利用例およびValidation
- 探索のみで、現時点では製品保証に使用しないもの

本家由来であることだけではACL適合性を十分に証明したとみなさない。
探索や個人的関心から始まったテストでも、現在の公開契約を適切に観測するなら、根拠を確認した上で正式な品質資産として扱うことができる。

各テストまたはテスト群について、可能な範囲で次を確認する。

- 出所または追加理由
- 対象となるAPI・仕様・品質要求
- 入力領域と観測する結果
- 実行条件と除外条件
- Debug／Releaseなどの構成
- 対応platformおよびtoolchain
- 自動実行、定期実行、手動実行、探索の別
- 失敗、skip、not runの意味
- 証明できる範囲と証明できない範囲

由来や目的を確認できない場合は、推測で確定せず不明として残す。

同じ由来、公開契約、実行条件、および証拠限界を持つものは、それらの根拠を失わない範囲でテスト群として管理できる。個別テスト関数への台帳付与自体を目的にしない。

## 7. ドキュメントとの関係案

利用者向けドキュメントは、少なくとも次の情報への到達経路を提供する。

- パッケージの目的と提供範囲
- 導入方法と対応環境
- APIの目的、基本的な使用例、および計算量
- 事前条件、失敗条件、および保証境界
- 本家 ac-library の対応機能と意図的な差異
- 提供する版・系列、その現在の配布経路、toolchain、および互換性の考え方
- アンダースコア付き宣言など、互換性保証対象外の範囲

利用者向け文書と、保守者向けの品質要求、検証記録、テスト由来、評価証拠、および残余リスクは分離する。
ただし、利用者の選択や安全な利用に必要な制約を内部資料だけに閉じ込めない。

文書が存在することだけで理解可能性を確認済みとせず、実際のAPIおよび利用シナリオとの整合を評価する。

## 8. 今後具体化する事項

本原案では、次を確定しない。

- 基準とする本家 ac-library の版またはcommit
- ACL適合性に含める互換性の次元と許容する差異
- 提供対象のアルゴリズムおよび公開API
- 「製品レベル」の具体的な意味と受入水準
- 競技用途と一般Swift用途の優先順位および保証範囲
- 対応するSwift、platform、architecture、およびbuild configuration
- Debug、Release、`-Ounchecked` の保証境界
- 性能の比較対象、workload、環境、および判定水準
- 各品質要求と既存テスト・CI・文書との対応
- APIドキュメントの媒体、構成、および公開方法
- リリース判定、品質ゲート、および残余リスクの許容条件
- モジュール別または機能別の品質プロファイルが必要か
- 本原案を正本化する条件と手続き

これらは、既存資産の棚卸しと利用目的の確認を踏まえ、独立した判断として具体化する。
未確定事項を、現在の実装、テスト配置、CI構成、または文書によって既成事実化しない。
