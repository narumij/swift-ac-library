# Quality Model Application Principles — Draft

> **文書状態:** 暫定試験から得た下位の適用原則案。製品品質要求の正本、個別moduleの要求、受入条件ではない。

## 1. 目的

`QUALITY_REQUIREMENTS_DRAFT.md`のQR-01〜QR-07を個別対象へ試験適用するとき、証拠の強さを過大評価せず、対象規模に不釣合いな管理を増やさないための共通手順候補を置く。

## 2. 適用前にscopeを固定する

少なくともproduct、提供系列、target、source、test、platform、toolchain、build条件、比較対象を識別する。同名・類似実装、互換source、fixture、実験targetの結果を自動的に合算しない。

internal実装は、公開上の保証が実質的に依存し、対象とする品質特性に関係する実行経路まで含める。共有utilityの全利用先を無制限に追跡しない。

## 3. 証拠量を比例させる

全QRについて対象との関係を確認することと、全QRへ同じ量の証拠を要求することを分ける。具体化と証拠の深さは、公開契約、risk、本家との差異、主張する保証の強さに応じて決める。

利用頻度は調査・実施の優先順位には使い得るが、公開した正確性または安全性の保証を弱める理由にはしない。

「論点が少ない」「対象外」「未検証」「確認済み」を区別する。複雑な対象のchecklistを単純な対象へ機械的に複製せず、単純であることだけを確認済みの根拠にもしない。

## 4. testを複数の軸で分類する

由来と現在の役割を分ける。

- 本家testとの内容上の対応
- Swift固有の契約または実装差異
- 興味・実験から生まれた観測
- 回帰防止、death test、compile fixture、性能観測、Validation候補

同じ由来、契約、実行条件、証拠限界を持つtestは、根拠を失わない範囲で群として扱える。個別test関数への一律な台帳付与を必須にしない。

## 5. 実行状態と品質上の意味を分ける

次を別々に記録する。

1. sourceに存在する
2. compile条件で有効になる
3. test planに列挙される
4. 選択実行された
5. passed、failed、skipped、not runになった
6. どの品質上の主張を、どの限界で観測できる

成功数、CI全体成功、test名、由来だけで契約適合を主張しない。失敗やsignalも、原因確定前に隠さず反証として保持する。

## 6. 棚卸し用test

契約上の位置づけが未決でも再現価値のあるtestは、通常観測を`Tests/AtCoderTests/EtcTests.swift`、process isolationを要する観測を`Tests/AtCoderTests/DeathTest.swift`へ置ける。

棚卸し用testは名前とコメントで未決境界を示す。通常suiteを恒常的に失敗させる環境依存の反証は、観測結果を別記録へ残したうえでdisabledまたは明示選択対象にできる。disabledを問題解消と扱わない。

棚卸しでは、各testを既存module testへ移す、fixtureへ移す、条件付き検証として残す、削除する、または製品判断待ちにするかを決める。

## 7. 出力

暫定適用の出力では少なくとも、観測、解釈、下位要求候補、未確認、製品判断、証拠限界を分ける。一対象で得た事情を上位モデルへ直接一般化せず、横断比較を経て変更候補として提示する。
