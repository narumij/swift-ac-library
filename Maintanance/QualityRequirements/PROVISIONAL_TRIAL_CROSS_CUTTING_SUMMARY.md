## 1. 目的

個別試験で見つかった事情を一対象から全製品へ一般化せず、複数対象で繰り返し現れたもの、対象固有のもの、まだ反証されていないものを分ける。

この要約は、後日のまとめレビューで次を判断する材料にする。

- 上位品質モデルの区分に重複、欠落、評価不能箇所があるか
- 比例的適用を上位モデルへ明記する必要があるか
- 下位品質要求、公開仕様、試験計画、運用原則のどこへ各論点を置くか
- 次の試験対象を増やす情報価値があるか

## 3. 対象の差

| 対象 | 主な性質 | 横展開で狙った反証 |
|---|---|---|
| SegTree | generic operator、直接storage、広いAPI、非コピー性 | 上位QRが複雑な対象の論点を分離できるか |
| DSU | 小さなAPI、Int storage、追加API、類似する別実装 | 単純な対象へ過剰な証拠量・管理負荷を課さないか |
| FenwickTree | 小さなAPI、generic数値変換、overflow、本家testとの広い対応 | test成功とSwift固有不変条件を分けられるか |
| SCCGraph | 小さな公開wrapper、内部algorithm、CSR、再帰DFS | 公開面が単純な対象で内部実行経路を落とさないか |

この4対象は製品全体の代表標本ではない。文字列algorithm、flow、modint、convolution、consumer導入、Linux、競技提出などは直接扱っていない。

## 4. 複数対象で維持された区分

### QR-01とQR-02

本家との対応関係と、Swift製品自身の公開契約は全対象で別の問いになった。

- 本家と直接対応するtestがあっても、Swift追加APIや所有権設計は残る。
- 本家との差異があっても、説明された差異として採用する余地がある。
- 基準版が未決なら、固定commitとの比較結果を製品適合へ昇格できない。

現時点で一方を他方へ統合できる根拠は得られていない。

### QR-03

計算量を意図する実装、large input test、XCTest measureの存在は、それぞれ外部比較可能な性能適合とは別だった。全対象へ同じbenchmarkを要求する必要はないが、性能価値を主張する操作には対象、規模、環境、受入水準が要る。

### QR-04

正しい出力だけでは、所有権、要素寿命、手動storage、bitPattern変換、再帰深さ、assert無効構成、`@unchecked Sendable` を扱えなかった。

一方、必要な確認は対象ごとに異なる。

- SegTree: generic要素寿命とoperatorを含む。
- DSU: Int固定storageのため要素寿命論点を縮小できる。
- FenwickTree: 数値表現とgenericなゼロ初期化が加わる。
- SCCGraph: 公開wrapperではなく内部CSRと再帰実行経路を見る必要がある。

QR-04を維持する根拠候補は増えたが、共通checklistを全件へ課す根拠は得られていない。

### QR-05とQR-06

契約を理解できることと、実際にtarget、toolchain、platform、consumer環境で利用できることは別の問いとして現れた。文書の存在だけでもbuild成功だけでも、他方を代替しない。

### QR-07

本家由来test、Swift固有test、death test、互換source、実験target、共有internal実装を混同しないための追跡可能性が全対象で役立った。

ただし、製品・設計の保守可能性と品質情報を次工程へ接続する運用能力の所属は、今回も決まっていない。

## 5. 横断して得られた原則候補

以下は上位モデルへの採用決定ではなく、複数対象から得た候補である。

### 適用前に評価scopeを固定する

同名または類似するsourceとtestがあっても、core product、互換系列、fixture、実験targetを自動的に合算しない。scope決定は各QRの評価以前に必要になる。

### 全QRを見ることと、同量の証拠を要求することを分ける

各QRが対象へ意味を持つかは確認するが、対象の公開契約、risk、差異、および主張する保証の強さに応じて具体化と証拠の深さを変える。利用頻度は調査や実施の優先順位には使い得るが、公開した正確性・安全性の保証を弱める根拠にはしない。

「論点が少ない」「対象外」「未検証」「確認済み」は異なる。単純な対象だから確認済みとはしない一方、複雑な対象のchecklistを機械的に複製しない。

### 公開API面だけで安全性scopeを閉じない

公開上の保証が実質的に依存する実行経路と、その品質特性に関係する範囲では、internal storage、共有utility、型変換、再帰性も対象になる。依存関係を無制限に追跡せず、internal implementationの詳細をそのまま利用者向け契約へ露出する必要もない。

### testの由来と現在の役割を二軸で扱う

本家testとの直接対応、Swift固有test、興味・実験由来のtestは、現在観測できる品質特性によって再評価できる。本家由来という事実だけで適合を証明せず、独自testという事実だけで品質資産から除外しない。

同じ由来、契約、実行条件、証拠限界を持つtestは、根拠を失わない範囲で群として扱える。全test関数へ個別台帳を要求する根拠は得られていない。

### test状態を分ける

少なくとも次を混同しない。

- source上に存在する
- compile条件で有効になる
- test planに列挙される
- 選択実行された
- 成功、失敗、skip、not runになった
- 品質上の主張を観測できる

Xcodeの一覧には `#if false` のtestも現れたため、列挙だけを実行可能性や証拠へ読み替えない。

### 既存testが固定する振る舞いを自動的に契約化しない

返却順、追加API、assert時の終了、overflow、内部helperなどをtestが観測していても、それを製品が保証するかは別の製品判断である。

## 6. 対象固有として保持する事項

次は他対象へ一般化せず、当面は個別記録または下位要求候補へ残す。特にFenwickTreeのゼロ初期化とSCCGraphのdeep recursion／CSRは、品質モデルの欠陥とは扱わず、必要性とscopeを別に定める独立した技術調査候補とする。

- SegTreeのoperator、generic要素寿命、用途限定public API
- DSUの `unite`、`reset`、`clone` とweighted別実装
- FenwickTreeのgeneric文脈における `-1` によるゼロ初期化、bitPattern、対応数値型
- SCCGraphのcomponent返却順、internal CSR、deep recursion
- Swift 5.8.1向け各別実装の手動解放と提供上の位置づけ

## 7. 上位モデル修正候補

今回の4適用から、QR-01〜QR-07の追加、削除、統合を必須とする反証は得られなかった。

レビュー対象になり得る修正候補は、要求項目の追加より次の適用原則である。

1. 上位QRは評価領域と方向を定め、個別適合にはscope、強度、達成水準、証拠、受入条件が必要であること。
2. 各QRの適用可能性は確認するが、公開契約、risk、差異、および主張する保証の強さに応じて下位要求と証拠量を比例させること。利用頻度は調査・実施の優先順位とし、公開保証を弱める根拠にしないこと。
3. 評価scopeを、product、系列、target、実験に加え、公開上の保証が実質的に依存し、その品質特性に関係するinternal経路の境界を含めて先に固定すること。
4. testの由来、現在の役割、実行状態、証拠限界を区別すること。

これらが既存原案ですでに十分読めるか、明文化が必要かはレビューで判断する。試験記録から直接原案へ書き戻さない。

## 9. まとめレビューで確認したいこと

1. 個別記録が品質判定へ逸脱せず、観測、推定、未確認、候補を分離できているか。
2. 4対象から比例性を候補として挙げることが過度な一般化になっていないか。
3. scope固定、内部実行経路、test状態の区別を上位モデルへ明記すべきか、下位試験原則へ置くべきか。
4. QR-01〜QR-07に、統合可能な重複または分類できない関心が残るか。
5. FenwickTreeのゼロ初期化とSCCGraphの再帰・CSRを独立した技術調査へ進める場合、その目的、scope、優先順位をどう定めるか。
6. 次に別対象へ広げる情報価値があるか、ここで上位モデルと下位要求構造のレビューへ移るべきか。
